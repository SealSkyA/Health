# 「壹健康」检查报告管理系统 · 2026 年 10 月医保相关数据异常分析报告

- 分析对象：`3HealthTrends/backend`（FastAPI + SQLAlchemy）
- 数据库：`backend/3healthtrends.db`（SQLite，`DB_DRIVER=sqlite`，即本库为实际业务数据源）
- 分析日期：2026-11-10
- 分析人工具链：Python 内置 `sqlite3` 直查 + 模型对照

> **重要前提（数据可用性结论）**：本系统在本地 SQLite 库中**没有任何 2026 年 10 月的医保业务数据**。
> `reports`、`report_docs`、`prescriptions`、`medication_items`、`stored_files` 等业务表全部为 **0 行**。
> 库内仅有 schema + 系统管理数据（1 个 admin 用户、8 条系统配置、3 条登录日志）。
> 因此本报告 **不做虚构填充**，第 2/3 节"异常检测"分两层：
> ① **现状可确认的异常**（数据完整性/结构/安全层面的真实异常，有直接证据）；
> ② **已就绪的"月份业务异常"检测规则**（供业务数据落地后自动套用，当前因无数据无法判定命中）。
> `deployment/` 下的 `uid1_now.json`、`uid4_*.json` 等均为 **AI 问数会话快照**（`{ver,groups,sessions}`），非医保业务数据。

## 2. 异常检测

### 2.A 现状可确认的异常（有直接证据）

| 编号 | 异常类型 | 位置/证据 | 详情 |
|---|---|---|---|
| **A1** | **业务数据全空（严重）** | `reports/prescriptions/medication_items/stored_files/report_templates` 均 0 行；`report_docs` 表缺失 | 上线至 2026-11-10 库中无任何检查报告/开方记录，无法做 10 月医保业务统计 |
| **A2** | **模型与库表结构漂移（严重）** | `reports` 库表缺 `user_id/category/items_json`；`prescriptions` 缺 `user_id/report_id/check_time/start_date/end_date`；`stored_files` 缺 `user_id`；`ai_models` 缺 `alias/api_key` | 代码 `Report(user_id=…, category=…)`、`Prescription(user_id=…)` 直接 INSERT 会抛 `OperationalError: table xxx has no column named …`；`report_docs/roles/role_perms/ai_analyses/ai_agent_tasks/ai_chat_sessions/report_interests` 整表未建。属 `create_all` 旧库未随模型演进迁移 |
| **A3** | **安全弱配置（高）** | `.env`：`JWT_SECRET=change-this-to-a-random-string`（30 字节）、`ADMIN_PASSWORD=change-me`；`config.py` 兜底 `dev-secret-change-in-production`；`_server.log` 记录 `InsecureKeyLengthWarning: HMAC key is 30 bytes < 32` | 默认/占位密钥未替换，HS256 密钥过短，存在越权/伪造 token 风险 |
| **A4** | **登录失败痕迹（中）** | `login_logs` 2 条 401 失败（2026-10-25 07:38:25/29，Chrome，IP 127.0.0.1）；`_server.log` 同接口 07:38 两次 401 | 同一账号短期内连续失败 2 次，且设备与首次 Python 客户端不同；与当日 `PUT /api/auth/change-password` 返回 400（修改密码失败）时间相近，疑似改密/重登录过程凭证不一致，或口令试探 |
| **A5** | **必填约束缺口（低/中）** | `reports` 除 id 外几乎全部可空；`categories/机构/医生` 无必填；库表 `report_count INTEGER NOT NULL` 但无服务端默认值（仅靠模型 default=0），跨客户端/脚本直连插入易缺列 | 业务分析所需"机构、检查时间、类别"允许为空，后续统计口径不稳 |

### 2.B 已就绪的"月份业务数据"异常检测规则（当前无数据，待业务数据落地后套用）

> 参照系统内 `backend/app/routers/ai.py::_h_stats` 的统计口径（`check_records/reports/prescriptions/category_dist/abnormal_top`），建议对其扩展出按月检测规则。以下规则均已定义 SQL 判据，但 `reports` 等表为 0 行，**无法命中，全部判定为"待数据验证"**。

| 检测维度 | 判据 / 阈值（建议） | 依据字段 |
|---|---|---|
| 空值率 | 必填字段（机构/检查时间/类别/开方医师）空值占比 > 0 | `addr, checked_at, category, doctor` |
| 重复报告 | 同 `user_id + checked_at(±1天) + addr` 出现 > 1 条 | `reports` |
| 重复明细 | 同 `prescription_id + name + spec` 重复 | `medication_items` |
| 时间不合理 | `checked_at` 未来（>now）或早于建库；年≠2026；文本型时间戳混入 | `reports.checked_at` |
| 环比突变 | 10 月 vs 9 月业务量激增/骤降（如 ±300%） | 按月 count |
| 数值异常 | 金额为 0/负/超大、数量突变（**注：当前表无费用/数量字段**，需先落地费用模型） | 待新增费用列 |
| 异常项占比 | `result != normal` 的明细占当月比例突变 | `report_docs.items_json` |

**当前结论**：A1 是根因——没有业务数据，2.B 中所有"10 月业务异常"均无法判级，只能给出规则；A2 结构漂移若不修复，即使录入业务数据也会写入失败。

## 3. 原因分析（含确定性标注）

| 异常 | 可能原因 | 确定性 |
|---|---|---|
| A1 业务表全空 | ① 系统仍在开发/演示阶段，`3healthtrends.db` 只是本地初始库，业务数据存于生产 MySQL 未落到本地；② `create_all` 建表后尚未通过 UI/API 录入任何报告与开方 | **可能**（更可能为①，`.env` 虽指向 sqlite 但部署脚本/`deployment/_migrate*` 显示曾对接 MySQL） |
| A2 结构漂移 | `Base.metadata.create_all` 仅建"缺失表"，对已存在旧表**不改列**；后续模型（`user_id/category/items_json`、`report_docs`、`roles` 等）在旧库已建之后新增，未做迁移（无 Alembic），导致"代码新列未落库、新表未建" | **确定**（代码与 `PRAGMA table_info` 比对可直接证实） |
| A3 弱安全配置 | `.env` 使用模板/占位默认值部署，未执行"强制改密"流程；`config.py` 兜底默认值同样弱 | **确定**（值即占位符文本） |
| A4 登录失败 | 当日修改密码（`change-password` 400）后再次登录时使用旧密码/输入错误，或存在尝试性访问 | **可能**（`login_logs` 与日志透明，但无法确认操作者意图） |
| A5 必填缺口 | 模型刻意将业务字段设为 `nullable=True`（注释"存量数据归 admin 可见"），设计上放宽约束，录入层未强校验 | **确定**（模型可空声明 + 注释佐证） |

## 5. 优化建议（按优先级）

**P0 — 先让数据能"落得进、算得出"（结构性）**
1. **引入数据库迁移机制**：为该项目接入 Alembic（或至少提供一次性 `ALTER TABLE`/`CREATE TABLE` 迁移脚本），把 `reports/prescriptions/stored_files/ai_models` 缺列，以及 `report_docs/roles/role_perms/ai_analyses/ai_agent_tasks/ai_chat_sessions/report_interests` 缺表全部补齐，与当前模型对齐。上线前以 `PRAGMA table_info` 做自动化 schema 对账，杜绝"代码能跑、库建不出来"。
2. **数据落地与生产回切**：确认 10 月医保业务数据在生产 MySQL；本 local 库仅作开发。定期将生产数据快照同步/导入本地做可复现分析，并对 `reports`（检查记录）、`prescriptions`（开方）、`report_docs`（单份报告+明细）建立可查询的测试库。

**P1 — 数据质量与录入校验**
3. **必填/约束收紧**：`reports.checked_at`、`addr(机构)`、`category(类别)`、`prescriptions.prescribed_at`、`org_dept(机构/科室)` 设为必填；前端表单 + 后端 Pydantic 双端校验；`report_count` 与各类统计字段给服务端 `SERVER DEFAULT`，避免跨端直连缺列。
4. **去重约束**：对 `reports` 增加"同 user + 检查日期 + 机构"的应用层/部分唯一约束防重复报告；对 `medication_items` 按 `prescription_id + name + spec` 去重；可加 `checked_at` 索引提升按月聚合。
5. **时间与数值校验**：`checked_at/prescribed_at` 不得晚于当前时间、年份与 TZ（Asia/Shanghai）一致；金额/数量字段落库前做非负、上限与精度校验。

**P2 — 安全配置（应立即执行）**
6. 替换 `JWT_SECRET`（≥32 字节随机值）与 `ADMIN_PASSWORD`；把 `config.py` 兜底默认值改为强制不允许生产直通（缺失即拒绝启动），并清理日志中的 `InsecureKeyLengthWarning`；对登录失败建立告警与阈值限制。

**P3 — 统计与月报监控**
7. 在 `ai._h_stats` 基础上扩展**按月业务看板**：月报告/开方量、按机构·科室·类别·检查项的分布、异常项 Top（复用其 `abnormal_top` 逻辑）、环比（当月 vs 上月）突变告警（阈值阈值化，如波动 > 300% 或新增量为 0 触发）。
8. 建立**月度数据质量体检脚本**，落地 2.B 规则：空值率、重复率、时间异常、金额/数量异常（0/负/超大）、与上月比对，输出结构化结果；并补充**费用/医保字段**到模型中，否则"费用异常"维度不可达（当前结构无此列）。
9. **统计口径落成文档**：明确"10 月归属"以 `checked_at`（检查时间）为准、以 `prescribed_at`（开方时间）为辅，避免跨月口径摆动。
